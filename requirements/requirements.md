# 招待・ペアアンケート・段階報酬キャンペーン 要件（index）

作成日: 2026-09-02 / 状態: **未実装・要件確定途中**
生成元: requirements-discovery（Stage 0〜8）

## 背景と目的

**目的は2つだけ。参加率の向上と、新規会員の獲得。**

段階報酬・ペア・招待は別機能ではなく、**1本の導線**として設計する:

```
招待リンクで友だちを呼ぶ
 → 相手が会員登録（招待報酬）
 → 2人ともがペア設問に回答（ペア報酬・答え合わせ）
 → 呼んだ人数でステージが上がる
 → 上のステージほど一括ボーナス
```

3つを別UIに割ると、どれも中途半端に埋もれる。専用ページ1枚に集約する。

参考: Looop「ハッピーサマー＋1℃ミッション」（段階解放・ゲージ）。
ただし**団体戦は採用しない**（下記 D-2）。

## 確定要件（decisions）

| # | 決定 | 内容 |
|---|---|---|
| D-1 | **立ち上げ期は「規模」を一切見せない** | 参加人数・累計回答数・全体ゲージ・ランキングは表示しない。少人数だと「12人が参加中」は過疎の証明になり逆効果。見せるのは自分の進捗と自分を招待した1人だけ。規模が武器になるのは規模が出てから |
| D-2 | 団体戦は不採用・**個人の段階報酬** | 団体戦は1タップの質を問わないため成立する形式。Hibi は品質係数で重み付けする前提（`qualityScore.ts`「正直が最も得な報酬設計」）と正面衝突する。また他人の進捗に報酬が左右されると「協力するほど上がる」個人体験にならない |
| D-3 | 「新規」の定義 | LINE友だち追加＋会員登録した人 |
| D-4 | **報酬トリガーは2段階** | 招待報酬＝会員登録時／ペア報酬＝招待された人が**アンケート回答完了**時 |
| D-5 | ペアの形 | ①招待型ペア（両者回答でボーナス）＋②相互回答（答え合わせ・一致率を見せる）。③リアルタイム同席は不採用 |
| D-6 | 紹介ランキング | **不要**。競争を煽ると回答の質が落ちる |
| D-7 | 招待ツリー可視化 | 不要 |
| D-8 | 報酬は**単価固定＋ステージ一括ボーナス** | 額の逓増は原資が読めない。青天井は業者に狙われたとき止められない。段階固定なら1人あたり上限が計算できる |
| D-9 | 本命報酬は後ろに置く | 登録だけで満額が出ると自作自演の回収が最速になる。「相手が実際に回答しないと本命が出ない」形にして不正コストを上げる |
| D-10 | **ペアは「回答原文を見せない」。一致/不一致の判定のみ返す** | 規約 v2.0 第10条4項(1)「回答原文を第三者に提供しない」にペア相手も該当する。かつ §7 は「ここを開けると守りの資産と営業文句を同時に失う」と明記。答え合わせの面白さは**原文開示から来ていない**——「一致→相違の順で見せる」設計は判定だけで完全に成立する。**規約改訂は不要になる** |
| D-12 | **キャンペーンは `scope` で二層にする** | 「参加率を上げる」には別物が2つある。**横断型(scope=platform)**＝プラットフォーム全体の活性・原資はHibi持ち出し・単位はユーザーの累計回答数。**案件指定型(scope=project)**＝この調査の回収率・**クライアント予算に乗せられる＝売り物になる**・単位は案件の目標回収数。テーブルも画面も1つで、`scope` の1列だけで切り替える |
| D-13 | **段は「回答」でも「招待」でも上がる（二本立て）** | 招待だけを条件にすると「協力するほど上がる」が「**人脈があるほど上がる**」になり、身内がいない人は開いた瞬間に詰む。招待は唯一の道ではなく**近道**（1人 ≒ 3回答）。回答は既にpt付与済みの行為なので**原資は増えない**。目的（参加率向上）にもより直接効く |
| D-14 | **分母のある数字は出してよい**（D-1の精密化） | 「12人が参加中」は過疎の証明だが「**50人中12人・あと38人**」は進捗に見え、残りが少ないほど「自分が入れば終わる」が効く。差は**分母の有無**。⚠ただし目標は `projects.max_respondents`、締切は `recruit_deadline` の**実データのみ**。未設定なら帯ごと出さない（分母の捏造＝honest copy違反）。偽の緊急性は作らない |
| D-16 | **山分けには1人あたり上限キャップを必ず付ける** | 景表法調査(2026-09-02)。懸賞制限告示第1項は「**価額を定める**こと」も懸賞に含む＋運用基準1(4)「価額に差等があり判別できない方法」＝山分けと構造が同じ。仮に懸賞と評価されると上限は**2,000円**(取引価額100円×20倍)。「少人数ほど有利」は**上限を制御できない**ので参加者10人で5,000pt/人＝即違反。キャップは既存の品質係数と同じ解き方（乗算だけだと制御不能→絶対キャップ）。詳細=[legal-premium-act.md](legal-premium-act.md) |
| D-19 | **全報酬に1人あたり上限2,000ptを適用し、全フェーズ着手可**（2026-09-04 ユーザー決定） | キャップにより仮に懸賞と評価されても限度額（100円×20倍）を超えない。弁護士確認は並行推奨・非ブロッカー |
| D-20 | **「ポイントを消費して抽選に参加」は絶対に入れない** | 賭博罪3要件（賭ける×偶然×得喪を争う）が揃う。ptはギフト交換可＝経済的価値あり。富くじ罪にも当たり得る。線引きは「外れたとき何かを失うか」——無料チケット→抽選はOK |
| D-17 | **「回答数が多いほど当選確率が上がる」設計は採らない** | 消費者庁Q19が「投稿すると当選確率2倍」を取引付随＝一般懸賞の対象とした。**確率を変えると規制対象化する分岐点**になる。「10問で**参加できる**」（参加資格）は「答えるほど**当たりやすい**」（確率変動）より安全 |
| D-18 | **性別で体験を出し分けない** | 「積み上げ」と「取り戻す」が別の動機であるのは有効な着眼だが、性別で当てると①外れる（積み上げ好きな女性も理想像に惹かれる男性もいる＝半数を取りこぼす）②**裏づけデータがない**（推測の分岐は検証できない）③外から説明しづらい。→**両方を同じ画面に置き、行動計測(migration 086)でどちらが効いたかを測る**。性別ではなく行動で最適化する |
| D-15 | **現在の段そのものを押せるようにする** | 「つぎの一手」を階段の外に置くと視線が階段から外れる。現在段に `あと3回` と `answer ›` を載せ、その場で答えられるようにする |
| D-11 | **ペア設問は選択式のみ**（自由記述を入れない） | 構造的に原文開示が起きない状態を作る。「軽い設問だから」という限定は規約上通らない（4項(1)に設問種別の例外はない） |

## 理想形（今回スコープ外を含む）

- 招待した人から相手へ催促を送れる（運営から催促すると鬱陶しいので**招待者経由**にする）
- 答え合わせの結果を起点に、ペア相手と継続的にやりとりする
- 招待経由ユーザーの定着率を計測し、招待報酬額をデータで調整する

## 実装可否の判定

**実装できる。** 既存資産の上に薄い層を1枚足す規模で、既存の「サイクル」機能より小さい。

| 必要なもの | 現状 | 判定 |
|---|---|---|
| 報酬キャンペーンの器 | `reward_campaigns`（032）が存在。`campaign_type='referral'` も定義済み | **器のみ**・下記 R-2 |
| ポイント付与 | `userPointService.awardPoints`。`idempotencyKey` で二重付与防止・`referenceType:"campaign"` 済 | **そのまま使える** |
| 品質による重み付け | `qualityFactor`/`basePoints`/`qualityReasons` が付与経路に配線済 | そのまま乗る |
| 進捗の可視化・演出 | 累進しきい値・メダリオン・`rank-celebration.ejs` | **流用できる** |
| LIFF URL生成 | `liffService` の `build*LiffUrl` 群 | **必ずこれ経由** |
| 回答UI | `partials/answer-ui.ejs` | 流用 |
| 日次バッチ | `cronDispatchService`（Workers Cron Trigger で稼働中） | 乗る |

新規に要るのは実質 **2〜3テーブル ＋ LIFF 2画面 ＋ API数本 ＋ 管理2画面**。

## 実装上の要注意（調査で判明）

| # | 内容 |
|---|---|
| **R-1** | **`user_points.pending_points` は流用できない。** 050 のトリガーは `exchange_request` のときだけ available→pending を動かし、それ以外の transaction_type は `ELSE` 分岐で **available に即時計上**する。「保留の招待報酬」をこの列で表現すると即座に使えてしまい、D-9 の不正対策が無効になる。**推奨: 確定時に初めて `awardPoints` を呼び、それまでは招待レコード側の状態として持つ**（ポイント台帳を汚さない） |
| **R-2** | `reward_campaigns` は**管理CRUDのみで付与配管がゼロ**（`rewardCampaignService` を呼ぶのは管理画面だけ）。かつ「1キャンペーン＝1回のボーナス」型で**ステージを表現できない**。拡張が要る |
| R-3 | ステージ達成ボーナスは `idempotencyKey` を `campaign:{id}:{lineUserId}:stage{n}` の形にして二重付与を防ぐ。既存の 23505 ハンドリングがそのまま効く |
| R-4 | ステージ達成判定は**必ずサーバー権威**。クライアントの進捗表示を信じない |
| R-5 | 招待URLは `liffService` のヘルパーで生成する。**`APP_BASE_URL` 直組みは過去に無限ループ事故を起こした箇所**（PR#37） |
| R-6 | 招待トークンは推測不能にする（連番・短い文字列は不可） |
| R-7 | 報酬は**単価を上げない**。`qualityScore` は「高単価だけが罰ゲーム化するのを防ぐ」絶対キャップ設計なので、単価を上げると噛み合わない。ボーナスで作る |
| R-8 | LIFFトークン失効の再取得漏れは過去に事故った箇所。招待ランディングは未ログイン可なので認証分岐に注意 |
| R-9 | 既存ナビ（探す/回答する/やりとり/マイページ）は**変更しない**。変えると migration 086 の行動計測の比較が切れる。バナー追加のみ |

## 不正対策（MVP必須・後付け不可）

招待は**ポイント＝現金同等物が直接流出する**。検出しても払った後の回収は現実的に不可能なので、設計で守る。

- 自己招待（line_user_id 一致）を弾く
- 複数アカウント自作自演 ← **最大の脅威**。D-9 の後ろ倒しで不正コストを上げる
- 同一端末の連続登録検出（migration 086 で UA/IP が取れる）
- 招待リンクの総当たり（R-6）
- 期限切れリンクの再利用を無効化
- 登録直後の退会→再登録に二度払わない
- 招待上限（A3）
- 品質基準を満たさない回答にペア報酬を出さない
- 不正確定時のポイント取消（`manual_adjustment` で減算）
- 監査ログ（争いになったとき復元できないと詰む）
