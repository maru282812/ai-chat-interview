# クライアントとアンケートの管理改修案

状態: 改修・本番デプロイ済み。検証記録は `client-survey-management-release.md` を参照。

## 目的

同じ依頼元から来たモニター配信案件と店舗専用アンケートを共通のクライアントで管理する。Box調査票のL1（管理用プロジェクト名）、E1（USER表示タイトル）、F1（クライアント名）を対応付け、確定番号で対象案件を検索できるようにする。

## 現行の問題と根拠

| 対象 | コード上の事実 | 改修方針 |
| --- | --- | --- |
| 店舗登録 | `src/controllers/adminController.ts:9885` のcreateStoreは法人・テンプレート・店舗名・店舗コードを必須とし、一括生成サービスを呼ぶ | クライアント登録・店舗登録・調査セット生成を別操作にする |
| 店舗DB | `supabase/migrations/096_industry_templates_and_stores.sql:79` はclient_id必須、industry_template_idは任意 | 業種テンプレート必須はDB全体の制約ではなく現在の作成経路の要件。法人への紐付けを無理に外す必要はない |
| クライアント登録 | `src/controllers/adminController.ts:10073` のcreateClientは名称だけでも登録可能だが、店舗専用画面へ戻り「店舗」と表示する | 共通のクライアント管理から登録できるようにする |
| 案件検索 | `src/lib/projectListFilter.ts:97` は管理名と運営メモの部分一致。確定番号専用項目なし | 番号・企業・管理年の独立検索を追加する |
| クライアント名 | `src/views/admin/projects/researchForm.ejs:228` は自由入力 | 共通マスタ選択にし、必要なら同じ導線から追加する |
| 公開区分 | 同ファイル336行付近のvisibility_typeは公開一覧に出すか専用URLだけにするかを決める | モニター/店舗専用という業務上の用途と公開設定を混同しない |
| A/B/C生成 | `src/services/storeProvisioningService.ts:158` の既定はpublished | 単なるクライアント登録からこのサービスを呼ばない。既存の店舗生成フローの公開挙動を今回無断で変えない |

実装はExpress + EJS + Supabase。Next.jsではない。調査はローカルコードが対象であり、本番DBやRLSの監査を完了した意味ではない。

## 提案する管理単位

1. **クライアント**: 依頼元の企業・施設・個人事業者。モニター用と店舗用で重複作成しない。企業コードをここに持たせる。
2. **店舗・施設**: クライアント配下の具体的な拠点。拠点を持たない案件では未指定でよい。実際の店舗を対象とするモニター案件なら指定できる。
3. **アンケート案件**: クライアントに紐付け、必要な場合だけ店舗にも紐付ける。案件ごとにモニター配信/店舗専用の用途を持つ。同一クライアント、同一店舗に両用途の案件を作れる。
4. **A/B/Cセット**: 店舗専用のうちテンプレートを使う場合の任意の作成方法。店舗専用案件すべてがA/B/Cとは限らない。

案件用途と公開区分は別。モニター配信でも招待者だけに回答させることがあるため、public/private_storeだけから用途を決めない。既存案件の用途が不明なら未設定を許容し、一括で推定分類しない。

## 画面案

現在の「店舗管理」を「クライアント・店舗管理」とし、次の操作を分ける。

| 操作 | 必要な入力 | 自動生成 |
| --- | --- | --- |
| クライアントを追加 | クライアント名、企業コード（既存Excelと対応） | 企業の管理情報のみ。業種・法人チェーン・QRコードは要求しない |
| 店舗・施設を追加 | クライアント、店舗/施設名、拠点識別情報 | 拠点情報のみ。業種テンプレートは不要 |
| アンケートを作成 | 管理名、USER表示タイトル、クライアント、案件用途、確定番号、管理年。店舗は任意 | 下書き案件 |
| 店舗用A/B/Cセットを作成 | 対象店舗、業種テンプレート、既存の生成用設定 | 従来のセット生成。重複生成と既存QRへの影響を検証する |

「業種」は実態の分類とアンケート生成用テンプレートを分けて表示する。モニター案件のために仮の美容室テンプレートを選ばせない。

## 番号と検索

- 確定番号はExcelで入力された番号を使用し、ACIで別に採番しない。表示は最低4桁、10000以上も扱う。
- 管理年・クライアント・企業コード・確定番号・管理用名を別々に検索できるようにする。確定番号の`1`と`0001`は同じ番号として一致させ、`0001`で`0010`まで拾う部分一致にはしない。
- 確定番号は企業ごとの連番なので、番号だけの検索結果は複数企業にまたがり得る。企業名と企業コードを結果に併記し、番号を全社共通の一意IDとして扱わない。
- 現行方針に合わせ、企業内の連番を年変更・削除・終了で再採番しない。DB上の一意制約を設計する際は既存データとA/B/Cの採番単位も確認する。
- 管理用名に番号が入っていれば現行の案件名検索でも部分一致はできるが、正確な番号検索や重複防止の代替にはならない。
- 既存案件の名称からの移行は、厳密に形式が一致し台帳とも照合できるものだけを候補にする。自動推測で全件を書き換えない。

## 変更範囲と順序

1. 共通のクライアント管理、案件からのクライアント選択を追加。既存clients IDは維持し、client_name文字列との対応が曖昧な案件は自動統合しない。
2. 案件識別用の管理年・確定番号と企業コード、用途の保存項目・入力・検索を追加。既存案件は未設定を許容し、Excelとの紐付けから埋める。
3. 店舗の登録だけを行う経路と、A/B/C生成の経路を分離する。既存のpartner連携、QR、サイクル、client別集計を維持する。
4. モニター案件をクライアントだけで登録・検索できること、同じ企業に店舗専用案件を追加できること、企業ごとの番号重複と検索、既存店舗のQR/サイクルが動くことを検証する。

関連範囲: adminController/adminRoutes、projectsとstoresのEJS、project/client/storeRepository、domain型、projectListFilter、Supabase migration、storeProvisioningService、既存のprojectListFilter/storeProvisioning/storeSurveyEntryテスト。

実装では案件用途はモニター配信/店舗専用/未設定を選択できる。確定番号は個別案件に手入力し、A/B/Cの自動生成では採番しない。スキルにも共通クライアント管理と用途の区別を反映した。
