# ポータルで作った調査票を、モニターにも配れるようにする

> 作成: 2026-09-22 / 設計メモ（未実装）
> 発端: 設問形式を8種に広げた結果、**作成画面は「モニター調査の調査票」も作れる形になった**が、
> 配信経路は店舗QRのまま。「その辺はどうする」への回答。
> 関連: [[gap-fastask-panel]]（回収管理のギャップ）/ [[plan-gt-cell-interview]]

## 0. 現状（コードで確認した事実）

### 作ったものは必ず店舗QRになる
`partnerSurveyService.ts:455-459` が**固定**している:
```ts
visibility_type: "private_store",
is_discoverable: false,
```
→ ポータルから作った調査票は**「探す」一覧に出ず、モニターにも配信されない**。
設問形式を広げても、**届け先は店舗の来店客だけ**。

### 課金は人数と無関係な定額
- `pricing.ts:144-145` … `qr_issue: 1` / `delivery: 1` の**定額2枚**
- `0001_init.sql:108` … `check (purpose in ('qr_issue','delivery'))`
  → **用途を増やすには migration が要る**（コードだけでは足せない）

### モニター配信に必要な材料は ACI 側に揃っている
| 要素 | 状態 |
|---|---|
| `visibility_type='public'` | ある（064 の CHECK に含まれる） |
| `is_discoverable`（探すに出す） | ある（040） |
| `reward_points`（謝礼） | ある |
| `apply_mode` auto/manual・応募 | ある（072） |
| セグメント配信（11属性・fail-closed） | ある |
| 指名配信ルール（14条件） | ある |

**足りないのは「ポータルからそこへ行く口」だけ**……ではない。下記が本題。

## 1. 🔴 先に直視すべきこと：パネルが 13 人

本番DBを数えた（2026-09-22）:

| 指標 | 実数 |
|---|---|
| `user_profiles`（配信可能な母集団） | **13** |
| うち `profile_completed` | **11** |
| うち通知可・未ブロック | **11** |
| `respondents` ユニーク `line_user_id` | 12 |

**この規模では「モニター調査」を商品として売れない。**
100サンプルの注文を受けても、**物理的に集まらない**。

### だから、この機能の位置づけは2通りに分かれる

| | 前提 | やること |
|---|---|---|
| **A. 商品として売る** | パネルが数千〜必要 | **パネル獲得が先**。機能を作っても在庫が無い |
| **B. 運営が自分で使う道具にする** | 13人でも成立する | 自社調査・テスト配信・少数への深掘り。**今すぐ価値がある** |

→ **まず B。** 作成画面（8種＋プレビュー）は既にあるので、
**運営が「この調査票をモニターにも配る」と決められる口**を足すだけで B は成立する。
A はパネル獲得の進捗に合わせて後から乗せる（設計は下記で先に決めておく）。

## 2. 論点：ポータルで作った調査票を、誰がモニター向けに転用するか

### 案1. 運営が管理画面から転用する（B向け・推奨）
- ポータルで作られた draft を、運営が ACI 管理画面で
  `visibility_type='public'` + `is_discoverable=true` + `reward_points` を設定して公開する
- **課金は既存のチケットに触らない**（モニター配信ぶんは個別見積り or 運営の自社利用）
- ⚠ **店舗QRとモニター配信を同じ案件で両立させない**（後述 §4）

**利点**: migration 不要・今すぐできる・13人でも回る
**欠点**: 運営の手作業が要る（セルフではない）

### 案2. ポータルに「配り先」の選択を置く（A向け）
作成画面に「誰に聞きますか」を足す:
- **自店のお客様**（店頭QR）… 今と同じ
- **YOTTOのモニター**（属性で絞って配信）… 新規

必要になるもの:
| # | 要素 | 規模 |
|---|---|---|
| a | partner API に `audience` を受ける口（`store` / `monitor`） | 小 |
| b | 目標サンプル数＋属性指定を受ける口 | 中 |
| c | **課金の新しい用途**（migration で `purpose` を追加） | 中 |
| d | 回収管理（目標比・自動締切）← [[gap-fastask-panel]] G1〜G5 | **大** |
| e | 謝礼の原資計算（いくら売っていくら払うか） | 中 |

**c〜e が無いと売れない。** とくに d は「100サンプル集める」の土台そのもの。

## 3. 課金の考え方（未決定・決めるための材料）

モニター配信は**人数に比例して原価が出る**（謝礼ポイント）。定額2枚では破綻する。

### 実測: 既存 public 案件の謝礼
`10, 10, 10, 30, 30, 30, 50, 60, 80, 100, 120, 150` pt
（1pt = 1円相当。`point_exchange_requests` は 500pt 単位で交換）

**100サンプル × 50pt = 5,000円が原価**（謝礼のみ）。
現行のチケットは1枚 39,800円なので、**定額2枚（実質1調査）でも粗利は出る**が、
サンプル数が増えると逆転する。300サンプル×150pt = 45,000円で赤字。

### 選択肢
| 案 | 内容 | 向き |
|---|---|---|
| **サンプル数×単価** | 「100サンプル ◯◯円」。ネットリサーチの標準。**原価と連動して赤字にならない** | A（売る） |
| **チケット枚数を人数で変える** | 50件=◯枚 / 100件=◯枚。購入動線を変えずに済む | A（売る） |
| **個別見積り** | LPの「リサーチプラン」と同じ扱い。**実績が出るまではこれで回す** | **B（今）** |

→ **B の間は個別見積り**でよい。A に進むとき「サンプル数×単価」に寄せるのが素直
（原価が人数比例なので、課金も人数比例にしないと必ずどこかで赤字になる）。

⚠ **決めるべきは「1サンプルいくらで売り、いくら払うか」**。
これは [[gap-fastask-panel]] G25（単価・原資計算が1行も無い）そのもの。

## 4. ⚠ 設計上の落とし穴（先に決めておく）

### 4-1. 店舗QRとモニター配信を同じ案件で混ぜない
同じ `project` に両方の回答が入ると:
- **集計で「自店の客」と「モニター」が混ざる**（性質が違うので混ぜると使えない）
- 店舗QRは謝礼なし・モニターは謝礼あり → **同じ設問で片方だけ報酬**という不整合
- `partner_readonly` / チケット消費の前提も変わる

→ **案件を分ける**か、最低限 `audience` を持たせて**集計で必ず分離**する。

### 4-2. 性年代の固定2問
partner 経由の案件は性年代2問が**自動で付く**（`partnerDemographics.ts`）。
モニターは `user_profiles` に性年代を**既に持っている**ので、
**同じことを2回聞く**ことになる。モニター向けでは外すか、プロフィールから埋める判断が要る。

### 4-3. 🔴 規約（利用目的）
店舗QR = 「その店舗に伝えるために答える」
モニター配信 = 「YOTTOの調査に答え、**法人に集計を渡す**」
→ **取得目的が違う。** 現行の規約v2.0 第9条3項は
「**店舗等への伝達を目的として設けた設問**」の開示しか認めていない。

**法人向けにモニターの回答を集計提供するなら、規約の新版が要る。**
しかも**利用目的の追加は遡及しない**＝新版を切る前の回答は使えない。
→ **A に進む判断をした時点で、すぐ規約を切る**（遅らせるほど使える回答が減る）。

### 4-4. 景品表示法
モニターへの謝礼は現行のポイント制で運用中。
**単価を上げる／抽選型にする**なら、取引付随性と限度額を再確認。

## 5. 進め方の提案

### いま（B: 運営の道具にする）
1. **ACI 管理画面で「この案件をモニターにも配る」を選べるようにする**
   （`visibility_type` / `is_discoverable` / `reward_points` の設定・**案件は分ける**）
2. 集計で `audience` を分離できるようにする（4-1）
3. モニター向けでは性年代2問を出さない（4-2）

→ migration 不要 or 最小。**13人でも今日から使える。**

### パネルが育ったら（A: 商品にする）
4. **規約の新版を切る**（4-3・遅らせない）
5. 回収管理（目標サンプル数・自動締切・属性クォータ）← [[gap-fastask-panel]] Step2
6. 課金の用途追加（migration）＋単価設計（§3）
7. ポータルに「配り先」の選択を出す（案2）

**5 が無いまま 7 を出すと、「100サンプル」と言われても止められない。**
