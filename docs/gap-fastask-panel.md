# Fastask 相当へ：モニターパネル調査の機能ギャップ一覧

> 作成: 2026-09-22 / 対象: `C:\work\ai-chat-interview`（ACI＝パネル本体・調査エンジン）
> 比較: Fastask（セルフ型ネットリサーチ）の機能連鎖
> **前提: モニター調達はできているものとする。** パネル規模・調達方法は論点にしない。
> 位置づけ: 実装着手前のギャップ分析。

---

## 0. 結論

Fastask の機能連鎖 **「ターゲティング → 目標n指定 → 配信 → 回収監視 → 締切 → 集計」** のうち:

| 工程 | 状態 | 一言 |
|---|---|---|
| ターゲティング | ⭕ **実装済** | segments 11項目＋指名配信ルール14項目。fail-closed まで作り込み済み |
| **目標サンプル数の指定** | ❌ **無い** | **概念がスキーマにもコードにも存在しない** |
| 配信 | ⭕ **実装済（6方式・むしろ過剰）** | 公募/指名/セグメント/デイリー/スワイプ/店舗QR |
| **回収監視（目標比）** | 🔺 部分的 | 完了数は見えるが「目標100に対し43」が出せない |
| **締切（n件で自動）** | ❌ **無い** | 募集締切と個人期限はあるが回収数と無関係 |
| 集計 | 🔺 部分的 | **rawdata は優秀**。画面の属性クロスが無い |

**つまり足りないのは「回収を管理する層」に集中している。** 配信とデータ出力は既に強く、間が抜けている。

## 🔴 第1優先：回収管理（Fastaskの中核で、ここが丸ごと無い）

### G1. 目標サンプル数（回収目標）— **概念が存在しない**
`quota` / `target_sample` / `sample_size` を全 grep しても実ヒット0（OpenAIのエラー文言と行動指標カタログの文字列のみ）。

**「100サンプル集める」案件が作れない。**

### G2. `max_respondents` が誤配線 — **実害あり**
`applicationService.ts:41-45` + `projectApplicationRepository.ts:117-125`:
```
.in("status", ["applied", "accepted"])   // ← 応募数。完了回答数ではない
```
実害:
1. `max_respondents=100` / manual → **応募100件で締切。当選30・完了20でも101人目は応募不可。目標100は永久に埋まらない**
2. 落とすつもりの応募者も枠を食う。かつ `UNIQUE(project_id, line_user_id)`(072:39) で**落選者は二度と応募できない**
3. auto でも同じ。**途中離脱した人の枠が戻らない**
4. **指名配信・セグメント配信・デイリー・店舗QRは `applicationService` を通らないので `max_respondents` を完全に無視**

### G3. 属性別クォータ（セル割付）— **無い**
「男性20代50・女性30代50」のセル別回収と、セル充足での自動クローズ。ネットリサーチの必須機能。**Fastaskとの最大の機能差。**

### G4. n件到達での自動締切 — **無い**
- `recruit_deadline`(072:9) = 募集締切（日付）
- `project_assignments.deadline` = 個人ごとの回答期限。しかも **`expireOverdueAssignments` は cron 未接続**で、管理画面を開いた時しか発火しない（`assignmentService.ts:488,867`）
- **「目標に達したら止める」が無い＝超過回収は謝礼の払いすぎ、未達は納品不能**

### G5. 回収進捗の可視化（目標比）— 部分的
`deliveryV2.ejs:18-33` は「配信対象/未回答/完了/完了率」= **assignments 母数に対する率**。目標比ではない。
`/exports/stat/status-counts`(adminRoutes.ts:96) が最もリサーチ的だが、エクスポート前の確認用。

## 🔴 第2優先：パネル台帳の整合（配信の分母が壊れている）

### G6. 母集団が二重で、どちらも正しくない — **最も根が深い**

| テーブル | 粒度 | 実態 |
|---|---|---|
| `respondents` | **(line_user_id, project_id) UNIQUE**(001:72) | 案件ごとに1行＝**延べ参加数** |
| `user_profiles` | **line_user_id UNIQUE**(015:2) | 実質のパネル台帳 |

**問題A: 友だち追加では `user_profiles` が作られない**
`conversationOrchestratorService.ts:1666-1670` → `respondentService.ensureRespondent`（実コード確認済）は `respondents` しか作らない。
→ **友だち1万人でも、プロフィール登録した人しか配信対象に入らない。**

**問題B: ダッシュボードの「回答者数」が延べ数**
`adminRepository.ts:11` → `respondentRepository.countAll()` = respondents 全行。1人が5案件に出ると5。
→ **パネル規模を誰も正確に言えない。** 法人に「モニター数」を提示できない。

### G7. キャンペーン配信の対象解決に穴 — **今すぐ直せる実バグ**
`adminController.ts:3103-3107`: セグメント一致した line_user_id を **`respondents` 経由で respondent_id に変換**してから配信。
→ **プロフィールだけ登録した会員（respondents 行が無い）は黙って落ちる。ログも出ない。**
→ さらに `deliverCampaign`/`assignManual` は **`notification_ok`/`is_notification_stopped`/`is_blocked` を見ない**（テンプレ配信とデイリーは見ている）。**配信停止希望者にも飛ぶ。**

### G8. セグメントUIと評価器の不整合 — **今すぐ直せる実バグ**
`segments/form.ejs:233` に `answer_count`（回答回数）があるが、`SUPPORTED_SEGMENT_FIELDS`(adminController.ts:2861-2864) に無い。
→ **保存はできるのに、配信時に fail-closed で丸ごと中止される「呪いのセグメント」が作れる。**
（デモseed `044:461` の `type:"rank"` テンプレも同理由で永久に実行不能）

### G9. 配信実績が全部デモデータ
`sent_count` を持つ行は `044:434-447` の5件のみ。かつ **`opened_count`/`started_count`/`completed_count` を更新するコードが存在しない**（`adminController.ts:3120-3124` は sent_count だけ）→ **ファネル3列は永久に0。**

## 🟠 第3優先：選考と集計（売り物の質に直結）

### G10. 選考画面に属性が1列も無い — **manual選考の存在意義が成立していない**
`applications/index.ejs:83-89,105`（実コード確認済）の列:
```
チェック / 応募日時 / 案件 / 応募者（LINE IDの生表示） / 状態 / 決定日時 / 操作
```
性別・年齢・地域・職業・quality_score・過去完了数が**全て無い**。ソートも属性絞り込みも無い。
→ **「20代女性を50人当選」が画面上で物理的に不可能。** 全選択で上から機械的に通すしかない。

### G11. 属性クロス集計が無い — **契約書で約束済み**
`researchOpsService.ts:449-` が **`user_profiles` を join しない**ため、性年代別の集計が原理的に出せない。
⚠ `063_import_contract_documents.sql:2031` の契約書テンプレに **「属性別クロス集計」が納品物として明記されている**。
（※ rawdata 側には属性が載る＝外部集計アプリなら可能。**ACI単体で納品物を作れないだけ**）

### G12. `/admin/projects/:id/analysis` が単純集計のみ
選択肢の度数 top12 のみ（`researchOpsService.ts:501-545`）。%なし・グラフなし・設問間クロスなし・有意差検定なし・ウェイトバックなし・回収率なし・スクリーンアウト集計なし。

### G13. ランク/連続ボーナスが案件完了で発火しない
`syncRank`/`recordAnswer` の呼び出しは **デイリー(`dailySurveyService.ts:514,530`)とスワイプ(`poolQuestionService.ts:201`)のみ**。
`pointService.awardCompletionPoints` は呼ばない → **本編アンケートを何本やってもランクが上がらない。**

## 🟡 第4優先：パネル運営の衛生（法的リスクを含む）

### G14. 退会導線が無い — **自社規約で約束済み（法的リスク）**
`063_import_contract_documents.sql:952-956` に自社のTODOがそのまま残っている:
> **退会機能の実装** — ユーザーが自分で退会・データ削除を申請できる導線を必ず設ける

現状 `/liff/projects/:id/withdraw`(liffRoutes.ts:186) は**応募の取り消し**であって退会ではない。
さらに `handleUnfollowEvent`(`:1672-1688`) は respondents を `dropped` にするだけで **`user_profiles` に触らない** → **ブロックした人が配信母集団に残り続ける。**

### G15. 配信オプトアウトの導線が無い — **特電法/LINE運用リスク**
`notification_ok` / `is_notification_stopped` は**読む箇所はあるが書くコードが0**。
会員も管理者も配信停止にする手段が無い（管理画面は「通知: OK/NG」の読み取り専用表示のみ）。

### G16. 配信頻度制御（疲弊対策）が無い
「1人あたり週n通まで」「前回から24時間空ける」が無い。複数テンプレが有効なら同じ人に重複して飛ぶ。
（`cooldown` のヒットは全て店舗サイクル/スワイプ再表示の別用途）

### G17. `is_blocked` / `fraud_flag` を立てるUIが無い
書き込みコード0。不良回答者を止めるには **Supabase コンソールで直接 UPDATE するしかない。**

### G18. 休眠復帰・属性更新依頼が「器だけ」
`dormancy_recovery` / `attribute_update_request` は**型とseedとCHECK制約だけ**で、送るジョブが無い（scheduler は morning/evening/reminder の3つのみ）。
`reward_campaigns` も **CRUD 30行だけで、ポイント付与から一切参照されない**＝永久に発火しない。

### G19. プロフィール入力率を上げる仕組みが弱い
完了してもバッジ（表示のみ）だけ。**完了ボーナスポイントが無い**（grep で付与コード0）。督促ジョブも無い。
→ G6と合わせて **配信可能な母集団が増えない構造。**

### G20. 属性の鮮度管理が無い
`occupation_updated_at` は書くだけで**読む側が0箇所**。「1年以上前の職業」を再確認する仕組みも、鮮度で配信を外す判定も無い。
`point_histories` に `attribute_update` 種別(050:46)があるが**発行するコードが無い**（属性更新に報酬を払う設計の未実装痕）。

### G21. パネル横断の重複回答制御が無い
案件単位のUNIQUEはある(072:39)が、**同一世帯/同一IPの複数アカウント検知が無い**。`ip_address`/`user_agent`(078) は **rawdata に出力するだけで自動照合しない**。「直近30日で類似案件に回答済みを除外」も無い。

### G22. 本人確認（KYC）が無い
LINEアカウント以外の本人性担保が無い。氏名・住所は自己申告（`address_declined`(015:9) で拒否も可）。
→ 高額謝礼案件・会場調査への展開時にブロッカー。

## 🟢 第5優先：商売の口（法人に売るなら）

### G23. 法人がパネル調査を発注する口が無い
`/api/partner` の全11本は **店舗QRスコープ専用**（作られる案件は常に `visibility_type='private_store', is_discoverable=false`）。
`partnerSurveyService.ts` に `segment` の文字が0件。**セグメント指定・目標n・パネル母集団に触れるパラメータが1つも無い。**

→ 現状パネル調査を売るなら **運営が管理画面で手作業**（案件作成→セグメント→配信→rawdata出力→外部集計→納品）。

### G24. 法人識別子が2つ併存して統合されていない
- `clients.id`（ACI・064:24-28。コメントに「任意・未使用でよい」）
- `projects.partner_store_id`（hibi-portal の `stores.id`・**別DB別採番**。089:11-16 が「別軸」と明記）

### G25. サンプル単価・原資計算が無い
「1サンプルいくらで売り、いくらをモニターに払うか」が1行も無い。`reward_points` は運営が勘で決める値で、売上と紐づいていない。謝礼の相場管理・上限下限バリデーションも無い。

### G26. 設問タイプが partner 経由では4種のみ
ACI本体は17種（マトリクス3種・順位付け・SD法・点数配分・一対比較）で **Fastaskより広い**のに、法人が使えるのは `single_choice`/`multi_choice`/`free_text`/`scale` の4種だけ。**マトリクスが売り物にならない。**

## ⭕ 既にある強み（作り直さない・Fastaskに勝つ部分）

1. **配信6方式** — 公募応募/指名ルール配信(14条件)/セグメント配信/デイリー/ついでスワイプ/店舗QR
2. **セグメント評価器が単一**（プレビュー・キャンペーン・デイリー・AIチャットが全部同じ評価器を通る＝「プレビュー10件なのに全員に配信」の再発防止が設計済み）＋ **fail-closed**（解釈できない条件は配信を止める）
3. **品質スコアリングが案件本編にも効く**（`pointService.ts:41`）— 直線回答・スピーダー・短答を検知。**Fastaskの「データクリーニング」相当が既にある**
4. **rawdata エクスポートが本格的** — SEX/AGE/AGE_BAND/PRE/REGION/JOB/BUS/MAR/INC/CHI/RANK＋UA/IP、Freeasy式列命名、コードブック自動生成、匿名化、監査ログ
5. **設問エンジン17種**（マトリクス・順位付け・SD法・点数配分・一対比較・ヒートマップ）
6. **AI深掘りインタビュー** — Fastaskに無い差別化
7. **ポイント/eGift交換**（500pt単位・pending分離・冪等・監査ログ）
8. **text設問に「比率主張に使わない」注記** を明示（誠実な集計設計）
