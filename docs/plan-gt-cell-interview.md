# GT集計表から「気になるセル」の回答者へ直接インタビュー

> 作成: 2026-09-22 / 参照: Fastask「FEATURE 04 業界初 気になる集計データから直接インタビュー」
> 位置づけ: 設計メモ（未実装）。[[gap-fastask-panel]] の G11（属性クロス集計）の上に乗る機能。

---

## 1. 何を真似るのか（スクショから読み取れる仕様）

Fastask の画面構成:

```
[ PRE | ARE | JOB | MAR | CHI | Q1 | Q2 | Q3 ... ]   ← 設問タブ
Q1 映画館に映画を見に行く時の楽しみや目的をお答えください

[回答者数上位3項目 ON]  [A インタビューできるモニター...]

GT表
        n      大きなスクリーン  新しい習慣や大画面  好きな俳優や  家族や友人と  一人で思いっきり  映画館は全く  その他
 総数  1000        372              351              147          92           492           201        10
 (%)  100.0%      37.2%            35.1%            14.7%        9.2%         49.2%         20.1%      1.0%
                                                                               ↑クリック
                                              ┌──────────────────────┐
                                              │ 現在 50人 / 492人が        │
                                              │ インタビューに参加できます  │
                                              │  [💬 インタビュー実施]     │
                                              └──────────────────────┘
```

**機能の本質**: 定量調査（GT表）から、**特定の選択肢を選んだ人だけを母集団として、そのまま定性調査（インタビュー）に接続する。**
「なぜその人たちはそう答えたのか」を、集計画面から1クリックで掘りに行ける。

分解すると4つの機能:
| # | 要素 | 説明 |
|---|---|---|
| ① | **顧客が見るGT集計表** | 設問タブ切替・n数と%の2段・属性列(PRE/ARE/JOB/MAR/CHI)も設問扱い |
| ② | **セルの選択** | セルをクリック＝「その選択肢を選んだ回答者」を母集団として指定 |
| ③ | **到達可能人数の表示** | 「50人 / 492人」＝492人が該当、うち**今インタビューに応じられるのは50人** |
| ④ | **インタビュー実施** | そのセグメントへ追加調査（インタビュー）を配信 |

---

## 2. なぜこの機能がうちに向いているか

**Fastask は人間がインタビューする。うちは AI が深掘りできる。**

- ACI には `display_mode='interview_chat'`（AI深掘り会話）が**既に実装済み**
- Fastask の「インタビュー実施」は日程調整・謝礼交渉・実施コストが乗る重い機能
- うちなら **セル選択 → AI深掘り案件を自動生成 → LINEでその場配信 → 数時間で定性データ** が成立する

→ **Fastask の「業界初」を、より軽く・速く・安くやれる。** ここは模倣ではなく上書きできる領域。

## 4. 🔴 最大の設計制約：規約が「識別子を返すな」と決めている

**ここを外すと法令違反になるので最初に確定させる。**

`partnerSurveyService.ts:596-620` のコメント（実装済みの現行方針）:
> ⚠ respondents へは「同意日時の突き合わせ」のためだけに読みに行き、
> **line_user_id / display_name / respondent_id はレスポンスに一切載せない。**
> answers → sessions で止め、**session_id すら返さない**（…回答者の名寄せに使われ得るため）

規約v2.0 第9条3項（migration 102 で追加した現行条文）:
> …当該回答の内容を、統計化又は匿名加工することなく、当該回答に係る店舗等に対してのみ開示することができます。
> この場合において、当方は、**ユーザーの氏名、LINEユーザーID その他ユーザーを直接特定する情報を併せて開示しません。**

### 結論：この機能は「顧客に人を見せない」形でしか作れない

| やってはいけない | 正しい形 |
|---|---|
| ❌ 顧客にセル該当者のIDリストを返す | ⭕ **人数だけ返す**（「492人該当・50人に到達可能」） |
| ❌ 顧客が個人を選んでインタビューする | ⭕ **顧客はセグメントを指定するだけ**。誰に配信するかはサーバーが決める |
| ❌ 顧客がインタビュー相手の属性個票を見る | ⭕ 回答は**集計または匿名で**返す |

→ **セル選択は「抽出条件」であって「名簿」ではない。** 識別子はサーバー内で完結させ、外に出さない。
これは現行 `getResults` の設計思想と完全に一致するので、**既存の作法を踏襲すればよい**（新しい原則を作らない）。

### さらに：追加調査（インタビュー）には利用目的の手当てが要る
- 規約9条3項は「**店舗等への伝達を目的として設けた設問**」の開示を認めたもの。**「過去の回答を元に再接触する」ことは書かれていない。**
- **利用目的の追加は遡れない**（既存回答を再接触の根拠にできない）
- → **規約の新版が必要**。本文差し替えでは再同意が発生しない（`consentService` は version_id 一致で判定）ので、**必ず新版を切る**
- 回答時に「追加のインタビューをお願いする場合があります」と**あらかじめ明示**する設計にすれば、9条3項と同じ作法で通せる

## 5. 実装の分解（Phase案）

### Phase 1: GT集計表を作る（顧客に見せる前に、まず作る）
**これが無いと以降が全部乗らない。** [[gap-fastask-panel]] G11/G12 と同じ作業。

- `researchOpsService.buildProjectAnalysisDataset` に `user_profiles` の join を足す
- 出力を **n行 + %行** の2段に（現状は度数のみ）
- 設問タブ（PRE/ARE/JOB/MAR/CHI = 属性も設問として並べる）
- ⚠ **`aggregation_type='qualitative_only'` の設問は比率を出さない**（`"Do not use for ratio claims."` の既存方針を維持）
- ⚠ **小N抑制**: n<10 のセルは%を出さない or マスク（`ai-analysis/report.ejs` に既存の n<3 抑制の前例あり）

### Phase 2: セル → 回答者抽出（サーバー内のみ）
- `answerRepository` に「question_id × 選択肢code で session_id を引く」メソッドを追加
- `answers → sessions.respondent_id → line_user_id` で名寄せ
  - ⚠ **`respondents` は案件ごとに1行**なので、`line_user_id` で distinct を取る（G6 と同じ罠）
- **到達可能人数の算出**（③の分子）。除外条件:
  - `is_blocked` / `notification_ok=false` / `is_notification_stopped`
  - 同意していない（追加調査の利用目的に同意した版を持たない）
  - **配信頻度制限**（G16。無いので作る必要がある）
  - 既にこの追加調査に配信済み
- ⚠ この人数は**変動する**ので、表示時と実行時で再計算する（AIチャットの承認カードが「承認時に件数再計算」しているのと同じ作法）

### Phase 3: 追加調査（AIインタビュー）の生成・配信
- セル条件から `display_mode='interview_chat'` の案件を生成
- 既存の `assignmentService.assignManual` に流す（配信経路は作らない・既存を使う）
- ⚠ 謝礼ポイントの設定が要る（インタビューは負荷が高いので通常案件より高く。**G25 の単価設計が無い**のが効いてくる）
- ⚠ **景品表示法**: 謝礼を上げる・抽選型にするなら取引付随性と限度額を確認

### Phase 4: 顧客に見せる（partner API / ポータル）
- `GET /api/partner/surveys/:id/gt` を新設（集計のみ・識別子なし）
- `POST /api/partner/surveys/:id/interviews` （セル条件を受け取り、人数を返す or 実行）
- ⚠ **既存 `getResults` のホワイトリスト方式を踏襲**（既定は非開示。新設問が黙って流れない）
- ⚠ 顧客に返すのは**人数と集計だけ**。個票・識別子は返さない（§4）

## 6. 先に決めるべきこと

| # | 論点 | なぜ止まるか |
|---|---|---|
| Q1 | **顧客に見せるのはどこまでか** | 集計のみか、匿名個票（1行=1人の回答）まで見せるか。後者は規約の書き方が変わる |
| Q2 | **インタビューは AI か人か** | AIなら即時・低コスト。人間なら日程調整と謝礼設計が要る。**AI推奨**（§2） |
| Q3 | **規約の新版をいつ切るか** | 再接触の利用目的は**遡れない**。**新版を切る前の回答は永久に使えない**＝早いほど良い |
| Q4 | **謝礼の単価** | インタビューは負荷が高い。G25（単価設計）が無いので併せて決める必要 |
| Q5 | **到達可能人数の定義** | 何を除外するか（頻度制限・同意・過去配信）で数字が変わる。顧客に見せる数字なので定義を固定する |
