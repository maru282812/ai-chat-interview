# 要件定義書: AIフロー作成（行動証拠による顧客発見）

> 作成日: 2026-07-27
> 元ネタ: ai-ideas プレイブック P13（行動証拠による顧客発見）／P16（滑り台コピーライティング）
> 位置づけ: 既存「AIフロー自動生成」（flowDesigner の生成モーダル → `buildGenerateFlowPrompt`）に**第2の生成モード**を追加する
> 対象読者: 本機能の実装・詳細設計を担当する AI エージェントおよび運営者

---

## 0. 本書の読み方

- **目的（§2）と機能要件（§6）には優先順位を付けてある。** 優先順位の低い項目のために高い項目を遅らせない。
- 本機能は P13 という「型」の移植であり、**型の核を崩す実装は受け入れない**（差し戻し条件 §10）。
- チャットで行動証拠がどこまで取れるかは未検証（§4 ギャップ）。**商品化（§2 目的5）より自社検証（§8 Phase構成）が先。**
- 未確定事項は §12 に集約。実装着手前に確定すべきものと、後で決めてよいものを分けてある。

## 1. 背景

### 1.1 P13 とは何か

P13 は YC「How To Talk To Users」由来の需要検証の型。核は次の式:

```
顧客仮説の1枚化（失敗条件を先に書く）
× 現在の行動を聞く（欲しい機能でなく、直近の具体的な1回を再現させる）
× 課題の経済価値の確認（頻度 × 時間損失 × 金銭損失 × 現行の支出）
× 購入に近い行動の要求（「良いと思う」でなく、予約・データ提供・決裁者紹介・有料パイロット）
→ GO / PIVOT / STOP 判定
```

一言でいうと**「思いつきの製品開発を、証拠に基づく開発へ変える順序」**。

### 1.2 なぜ Hibi でやるのか

- P13 の質問設計（直近の1回の再現・経済価値の確認・非誘導）は**人間がやると高コスト**で、AIチャットインタビューの得意領域そのもの。
- Hibi には既に土台がある: AI深掘り（probe）、非誘導プリセット `non_leading`、サーバー権威の設問フロー、AIフロー自動生成。
- Hibi を **「P13 実行装置」として商品化**する。商品名イメージ: **「新規事業の需要検証インタビューパック」**。アンケート事業・AI秘書事業の初回商談の前段に**自社でも使える**（dogfooding が最初の検証を兼ねる）。

### 1.3 P16 との接続

P16（滑り台コピー）は「材料無しの適用は上手いが刺さらない文章を生む」と明記しており、材料＝**顧客の生の言葉**の収集工程が欠けている。P13 インタビューで取れた verbatim を **LPコピー素材として構造化出力**すれば、Hibi が P16 の材料工場になる。

## 2. 目的（優先順位順）

| 優先 | 目的 | 判定基準 |
|---|---|---|
| **1（最重要）** | **「意見を聞く」でなく「行動を聞く」フローが生成される。** P13 の質問構造（直近の具体的な1回の再現）をそのまま AIフロー生成に実装する | 生成されたフローに「あったら便利ですか」「欲しいですか」型の意見設問が**含まれない**こと |
| **2** | **経済価値が構造化データで取れる。** 頻度 × 時間損失 × 金銭損失 × 現行支出を、集計可能な形式（numeric / 選択式）で確実に聞く | 経済価値4要素が全て設問として生成され、回答が数値・コードで保存されること |
| **3** | **GO / PIVOT / STOP 判定の材料が揃う。** 回答から判定基準の充足状況を運営者が確認できる | 判定基準ごとに「充足 / 未充足 / 不明」を突き合わせられること（判定自体は人間が行う） |
| **4** | **P16 素材（顧客の生の言葉）の構造化出力。** verbatim を LPコピー材料のカテゴリに整理して取り出せる | 問題の言語化 / 過去の対策と失敗理由 / ためらい / 得たい結果 / 代替手段 の分類で出力できること |
| **5** | **商品化（需要検証インタビューパック）。** 外販できる形に整える | 自社検証（§8 Phase 1〜2 の運用実績）を通過していること。**検証前に外販しない** |

**優先順位の意味**: 目的1が崩れたら目的2〜5に価値はない。目的4・5 は目的1〜3 が動いてからで良い。

---

## 3. 基本方針

1. **型を薄めない。** P13 の核（行動を聞く・経済価値・失敗条件・購入に近い行動）は生成プロンプトの都合で省略しない。「一般的な良いアンケート」に均されたら失敗。
2. **判定は人間、材料はシステム。** GO / PIVOT / STOP をシステムが断定しない。基準の充足状況と証拠を提示し、判断は運営者（＝事業主）が行う。
3. **製品を見せない・説明しない。** P13 の原則どおり、生成フローには製品説明・機能紹介・コンセプト提示の設問を含めない（インタビュー段階とユーザビリティテスト段階の分離）。
4. **既存アーキテクチャに従う。** Package First（プロンプトはBASE_PROMPT_TEMPLATES＋パッケージ版管理）、サーバー権威のフロー、既存のAIフロー生成の枠組み（新規モードとして追加、既存モードは無変更）。
5. **証拠の確度を正直に記録する。** チャットでは画面確認・資料確認ができない。取れた証拠の確度（発言のみ / 数値・固有名詞つきの具体的再現）を区別して残し、対面観察と同等であるかのように扱わない。

## 4. ギャップ（最初に認めておく制約）

P13 の原型は**対面観察（画面共有で実作業を見る）を含む**。チャットだけで行動証拠がどこまで取れるかは**未検証**であり、本機能の最大のリスク。

| P13 原型 | チャットでの代替 | 確度 |
|---|---|---|
| 実作業の観察（画面共有） | **不可**。直近の1回を時系列で再現させる質問で代替 | 中（発言ベース） |
| 資料確認（実際の支出額・外注費） | 数値を具体的に聞く（「毎月いくら」「直近の請求額」） | 中 |
| 発言の温度感・ためらい | 深掘り（probe）で「なぜ」「いつ」「誰が」を重ねる | 中 |
| 購入に近い行動（面談予約・データ提供） | 意向確認＋連絡先取得まで。実際の予約・決済は別導線 | 弱〜中 |

→ **だから Phase 1〜2 は自社案件（アンケート事業・AI秘書事業の需要検証）で先に回す。** 「チャットP13で GO 判定した案件が実際に売れたか」が本機能自体の GO / PIVOT / STOP 判定になる。

## 5. 全体像（何を作るか）

```
[管理者] flowDesigner「AIフロー自動生成」モーダル
   └ 生成モード選択: ①標準（既存・無変更） ②行動証拠による顧客発見（新規）
        └ ②選択時: 調査仮説シートを入力（対象者/課題仮説/現行手段/失敗条件 等）
             └ AI が P13 構造のフローを生成（8段階に対応する設問群）
                  └ 既存の設問編集・配信・回答・AI深掘りの仕組みにそのまま乗る

[回答者] 通常のチャットインタビューとして回答（P13 と意識させない）

[管理者] 回答収集後
   └ GO/PIVOT/STOP 判定支援レポート（基準充足の突き合わせ）
   └ P16 素材の構造化出力（LPコピー材料）
```

## 6. 機能要件（優先度付き）

優先度: **P0**＝これが無いと目的1〜2が成立しない ／ **P1**＝目的3を満たす ／ **P2**＝目的4〜5、後回し可。

### 6.1 生成モード選択（P0）

- flowDesigner の「AIフロー自動生成」モーダルに生成モード選択を追加する。
  - `standard`（既存。挙動・プロンプトとも**無変更**）
  - `behavior_evidence`（新規。本書の対象）
- 既存モードの回帰を作らないこと（差し戻し条件 §10）。

### 6.2 調査仮説シートの入力（P0）

P13 Phase 1「調査仮説の1枚化」に対応。`behavior_evidence` 選択時、生成前に以下を入力させる（プロジェクト名・調査目的は既存流用）:

| 項目 | 必須 | 用途 |
|---|---|---|
| 対象者（セグメント） | ✔ | 「1〜3教室の塾経営者」程度まで絞った記述を促す（プレースホルダで例示） |
| 調べる業務・場面 | ✔ | どの場面の行動を再現させるか |
| 課題仮説 | ✔ | 何に困っていると予想するか |
| 現行手段の仮説 | ✔ | Excel / 紙 / 外注 など |
| **失敗条件** | ✔ | 何が確認できなければ STOP か。**先に書かせる**のが P13 の核 |
| 利用者と購入者（同一か別か） | 任意 | BtoB で判定基準「購入者の困り」を見るため |

- 入力内容はプロジェクトに保存し、判定支援レポート（§6.6）で参照できること。
- **製品名・機能案は入力させない**（入力欄を設けない）。生成プロンプトに製品情報が渡らない構造にする。

### 6.3 P13 構造のフロー生成（P0）

生成されるフローは P13 の質問構造に従う。新規プロンプトキー（例: `buildGenerateFlowBehaviorEvidencePrompt`）を BASE_PROMPT_TEMPLATES に追加し、以下を生成規則として埋め込む:

**(a) 直近の具体的な1回の再現（フローの中心）** — P13 Phase 2 の10質問を基礎にする:

1. 直近でそれを行ったのはいつか
2. 最初から最後まで何をしたか（時系列で）
3. 誰が関わったか
4. どこで止まったか
5. 何時間・いくらかかったか
6. 失敗すると何が起きるか
7. 誰が改善を決められるか（決裁者）
8. 過去に改善しようとしたことはあるか
9. なぜその方法をやめたか
10. 次に同じ問題が起きるのはいつか

**(b) 経済価値の定量設問（4要素を必ず含む）**: 発生頻度（選択式）／1回あたりの時間損失（numeric）／金銭損失・外注費など現行支出（numeric）／現行手段への満足度（選択式）。

**(c) 購入に近い行動の要求（フロー末尾）**: 「良いと思うか」ではなく、次回ヒアリング（30分）への協力可否 → 可なら連絡手段、テストデータ・実物資料の提供可否、決裁者（意思決定する人）の紹介可否。

**(d) 生成禁止ルール（プロンプトに明記）**:
- 意見・願望設問（「欲しいですか」「あったら便利ですか」「いくらなら払いますか」）を生成しない
- 製品・サービスの説明やコンセプト提示を含む設問を生成しない
- 「普段どうしていますか」型の一般化質問で(a)を代替しない（必ず「直近の1回」を指定する）
- プロフィール既取得項目（年齢・性別・都道府県・職業）を聞かない（既存ルール踏襲）

**(e) research_goal の構造化**: 各設問の `research_goal` に P13 上の役割が分かるタグ（例: `[P13:recent_behavior]` `[P13:economic_value/frequency]` `[P13:commitment]`）を含め、§6.6 レポートと §6.7 出力が機械的に拾えるようにする。

### 6.4 P13 深掘りガイダンス（P0）

AI深掘り（probe）が P13 の流儀で掘るようにする:

- 「直近の1回」の再現が曖昧なら、時期・関係者・所要時間・金額の**具体を取りに行く**（「たとえば？」でなく「それは直近ではいつでしたか」「そのとき何分かかりましたか」）。
- 一般論・願望が返ってきたら、直近の実例に引き戻す。
- 誘導しない。既存の非誘導プリセット `non_leading` の上に P13 層を重ねる二段構成とする（`young_casual` と同じ積み方）。プロンプトパッケージ（例: `behavior-evidence-prompt`）として版管理する。

### 6.5 証拠の確度記録（P1）

回答（＋深掘り含む）から、課題ごとの**確度**を区別できるようにする:

- `発言のみ`（一般論・印象）／`具体的再現`（直近の1回を時系列で再現できた）／`数値あり`（時間・金額の具体値が出た）
- MVP では AI分析（§6.6 のレポート生成時）による事後分類でよい。回答時のリアルタイム判定は不要。
- 対面観察が無い以上 `数値あり` が上限であることをレポートに明記する（§3-5）。

### 6.6 GO / PIVOT / STOP 判定支援レポート（P1）

回答が一定数集まった後、運営者向けに判定材料を1枚で出す:

- **基準との突き合わせ**（P13 の運用基準をそのまま使う）:
  - GO 系: 同一セグメント5〜10人に聞けたか / 半数以上から同じ課題が独立して出たか / 直近の具体例が確認できたか / 現在時間・人手・金を使って対処しているか / 次に問題が起きる時期が分かるか / テスト協力の約束者数 / 購入に近い行動の獲得数
  - STOP 系: 課題が具体的行動として確認できない / 「あったら便利」しか出ない / 何も対処していない / 損失がない / **無料でもテスト協力が得られない**
  - PIVOT 系: 頻度が低い / 利用者は困るが購入者は困っていない / 現行手段に満足 / 特定属性だけ強く困っている（→セグメント絞り込み提案）
- **問題採点（100点満点）**: 痛みの強さ20 / 頻度15 / 時間・金銭損失20 / 現在の支出・代替行動15 / 緊急性10 / 決裁者接触可能性10 / 販売しやすさ10。**発言人数でなく、行動と損失が確認できた問題を優先**する集計にする（確度 §6.5 で重み付け）。
- 各判定材料に**根拠となる回答の引用**を付ける（数字だけ出さない）。
- システムは「基準充足: 7/7、STOP該当: 0」まで。**GO の宣言はしない**（§3-2）。
- 実装形態は管理画面AIチャットの分析ツール（Tier A 読み取り）が第一候補（§12-B1）。

### 6.7 P16 素材の構造化出力（P2）

回答から「顧客の生の言葉」を LPコピー材料として構造化出力する:

| カテゴリ | P16 での用途 |
|---|---|
| 問題の言語化（顧客自身の表現） | ヘッドライン・問題提起（顧客の語彙で書く） |
| 過去に試した対策と失敗した理由 | 「今まで解決できなかった理由」ブロック |
| 購入をためらう理由・不安 | 反論の先回り（8 Mile） |
| 本当に得たい結果 | 結果型ヘッドライン・理想の定義 |
| 比較している代替手段 | 競合＝Excel/現状維持 への差別化文脈 |
| 数字（頻度・時間・金額） | 抽象数字の体感化の素材 |

- **原文（verbatim）のまま**出力する。要約・言い換えで「AIっぽい文章」に変換しない（材料の価値は生の言葉にある）。
- 出力形式は Markdown（コピペ用途）を基本とし、CSV は任意（§12-B2）。
- 既存の統計エクスポート凍結契約（wide/long/codebook 列変更禁止）には**触れない**。独立した出力とする。

### 6.8 商品化パッケージ（P2・検証通過後）

- 「新規事業の需要検証インタビューパック」として、調査仮説シート → フロー生成 → 配信 → 判定レポート → P16素材出力 の一連を商品説明できる状態にする。
- 前提: §8 Phase 2 の自社検証で「チャットで行動証拠が取れる」ことを確認済みであること。**未検証のまま外販しない。**

---

## 7. スコープ外

- 実際の面談予約・決済・有料パイロット契約の機能（意向確認と連絡先取得まで。以降は人間の営業活動）
- 画面共有・ビデオ通話などの対面観察機能
- GO / PIVOT / STOP の自動確定（判定は常に人間）
- 既存 `standard` フロー生成モードの変更
- 統計エクスポート（wide/long/codebook）への列追加
- 回答者向け画面・LIFF の変更（生成されたフローは既存の回答UIにそのまま乗る）
- P13 以外のプレイブック（P14 一文説明・P15 証拠バンク等）の実装

| Phase | 内容 | 対応要件 | 出口条件 |
|---|---|---|---|

## 9. 受け入れ条件（Phase 1）

- [ ] 生成モーダルで `standard` / `behavior_evidence` を選択でき、`standard` の挙動が従来と完全に同一である
- [ ] `behavior_evidence` では調査仮説シート（失敗条件含む必須5項目）を入力しないと生成できない
- [ ] 生成フローに「直近の具体的な1回」を特定する設問が含まれる
- [ ] 生成フローに経済価値4要素（頻度・時間損失・金銭損失/現行支出・現行手段満足度）が numeric / 選択式で含まれる
- [ ] 生成フロー末尾に購入に近い行動の要求（ヒアリング協力・データ提供・決裁者紹介のいずれか複数）が含まれる
- [ ] 生成フローに意見・願望設問、製品説明、プロフィール重複設問が**含まれない**（10回生成して0件）
- [ ] 各設問の research_goal に P13 役割タグが付いている
- [ ] P13 深掘りプリセットを適用したプロジェクトで、一般論回答に対し「直近の1回」へ引き戻す深掘りが出る（深掘りプレイグラウンドで確認）
- [ ] 既存の全テストスイートが green（プロンプトキー追加は BASE_PROMPT_TEMPLATES と突き合わせる動的テストに追随させる。件数直書きに戻さない）

## 10. 差し戻し条件

- 生成フローが「一般的な満足度アンケート」に均されている（意見設問・仮定の質問が混ざる）
- 経済価値の設問が自由記述で生成され、集計できない
- 失敗条件を入力せずに生成・配信まで進める
- システムが「GO です」と断定表現でレポートする
- 深掘りが例示・誘導（「たとえばこういうことですか？」で選択肢を与える）をする
- P16 素材出力が原文でなくAIの要約・美文化になっている
- 既存 `standard` 生成の出力・挙動が変わる

## 11. 想定リスク

| リスク | 対策 |
|---|---|
| チャットでは行動証拠の確度が上がらない（本機能の根本リスク） | Phase 2 の自社検証を商品化より先に置く（§8）。確度分類（§6.5）で「発言のみ」比率を計測し、高ければ設問・深掘りを改良 |
| 回答者の負荷が高い（10質問＋深掘りは重い） | 対象は「案件インタビュー」枠（報酬あり・所要時間明示）。デイリー枠には載せない。所要時間の実測を Phase 2 で取る |
| 生成のたびに型が揺れる | 生成規則をプロンプトに明文化＋受け入れ条件「10回生成して意見設問0件」で検収。プロンプトパッケージの版管理で改良を追跡 |
| 経済価値の数値が信用できない（記憶ベースの申告） | 確度ラベルで区別し、レポートに「申告値」であることを明記。資料確認は営業段階の人間の仕事と割り切る |
| 「購入に近い行動」設問が営業的すぎて離脱を生む | 任意回答とし、文言は非誘導プリセットのトーンで生成。離脱率を Phase 2 で計測 |
| 対象者募集（P13 Phase 2 の「実際の潜在顧客と接触」）が Hibi の既存回答者層とズレる | 本機能は設問構造の提供であり、募集はスクリーニング条件＋外部リクルート（店舗QR等の既存導線）で対応。ズレる場合は商品側の提供範囲として明示 |
